# 下一阶段架构路线：六个可验证的特色点

本路线以当前 C++23 + Boost.Context Fiber、epoll/eventfd、HTTP/WebSocket、阻塞任务池和多副本部署为基础。这里的“特色”指**针对真实故障与性能边界做出可解释的设计和证据**，不宣称发明新算法。当前 [HTTP 基准](http_benchmark.md) 在指定小响应负载下测得 4 worker 慢于 1 worker；[排空设计](admission_and_drain.md) 已有静态连接上限，但还没有请求级接入控制和跨副本消息。现有 WebSocket 写入会等待 socket 可写，未来广播必须明确慢消费者预算。

每一项按“问题 → 最小接口 → 失败语义 → 对照实验 → 面试演示”验收。优先顺序为 1 → 6 的测试底座 → 2 → 3 → 4 → 5；不要在没有第 1 项证据前为吞吐量重写调度器。

| 序号 | 特色点 | 解决的实际问题 | 最小可演示结果 | 优先级 |
| --- | --- | --- | --- | --- |
| 1 | Fiber 感知的性能剖析与每 worker 观测 | 4 worker HTTP 反而较慢，原因未知 | 同负载下显示每 worker 的排队、唤醒、请求延迟与 CPU 热点 | P0 |
| 2 | 跨 Fiber/I/O/阻塞任务的 Deadline 与取消 | 客户端放弃请求后，下游工作可能继续占资源 | 超时或断连能及时取消等待并回收连接与任务槽位 | P0 |
| 3 | 请求级自适应并发接入 | 静态连接上限不能限制高成本请求的同时执行数 | 高负载时明确拒绝，比较 p99、吞吐与内存 | P1 |
| 4 | WebSocket/Stream 端到端背压 | 慢客户端占住写入 Fiber；后续广播还会放大发送缓冲需求 | 慢消费者占用受限，正常连接继续服务 | P1 |
| 5 | Redis Streams 跨副本事件通道 | WebSocket 客户端分散在不同副本，无法广播 | 两进程互发、断线后按 ID 补读、说明重复与保留窗口 | P2 |
| 6 | 可重复的故障注入与恢复矩阵 | “高可用”只有正常路径测试，缺少故障证据 | 延迟/断连/后端故障下无 fd 泄漏、无无限等待 | 贯穿各项 |

## 1. Fiber 感知的性能剖析与每 worker 观测

**切入点：** 为 `IOManagerPool`、`Scheduler` 和 HTTP 会话记录每 worker 的活跃连接、ready Fiber 数、post 队列深度、eventfd 唤醒次数、请求处理时间分布。热路径计数先用线程本地聚合，按窗口汇总，避免为了“观测”引入新的全局锁。保持指标开关或采样比例，测量观测开销。

**验收：** 固定编译器、CPU 亲和性、连接数、请求量和预热方式，重复 1/4 worker 对照；保存 p50/p95/p99、吞吐、CPU、分配和 perf 火焰图。给出能复核的根因或明确的排除证据，再决定是否改连接分派、唤醒或 HTTP 解析。不能以“4 线程一定更快”为验收条件。可逐步接入 [OpenTelemetry C++](https://opentelemetry.io/docs/languages/cpp/)；第一版无需依赖外部观测平台。

**面试讲法：** “先解释反常数据，再优化”，展示改前、定位、改后的相同负载比较。

## 2. 统一 Deadline 与取消

**最小接口：** `RequestContext { deadline, cancellation, request_id }`；`IOManager::waitReadable/WaitWritable` 与 `SocketStream` 接收剩余时间并处理取消；`BlockingExecutor` 在排队阶段可撤销任务，运行中的第三方同步调用依赖其自身超时和协作检查。不要把 C++ stop token 当作强制终止线程的能力。

**验收：** HTTP 客户端断开、服务排空和总请求超时分别触发取消；定时器和 epoll 注册都清理；不会将旧 fd 的事件送到复用该 fd 的新连接。测试覆盖取消与就绪同时发生的竞态、嵌套调用剩余预算递减，以及数据库调用无法立即中断时的清晰上界。

**面试讲法：** Fiber 只是执行方式，**资源生命周期和取消传播**才决定服务器能否在故障下维持容量。

## 3. 请求级自适应并发接入

**切入点：** 保留当前 TCP 连接硬上限作为最后一道资源边界；在 HTTP 解析后增加按路由或全局的在途请求计数。先实现固定并发上限与明确的 HTTP 503，再在相同负载下比较延迟反馈的自适应上限。限制值必须有最小/最大边界、采样窗口和回退开关，避免噪声导致抖动。可参考 [Netflix concurrency-limits 的设计](https://github.com/Netflix/concurrency-limits)；不直接照搬 Java 实现或声称自创算法。

**验收：** 逐步加压和突发流量两组实验中，比较固定上限与自适应上限的 p99、吞吐、拒绝率、VmHWM；正常流量下观测附加开销。连接已建立但请求被拒时返回 503；连接总数满额仍可能在 TCP 层直接关闭，两个层次分别计数。readiness、liveness 的语义维持清楚。

**面试讲法：** 说明“连接数”和“在途请求数”不是同一资源，为什么只限制 fd 不能保护 CPU 与后端。

## 4. WebSocket/Stream 端到端背压

**最小接口：** 每连接待发送字节预算 + 全进程总预算；写入队列达到上限时，显式选择暂停读入、拒绝新消息或关闭慢消费者，并记录原因。预算与 Fiber 生命周期绑定，断连/取消时归还。不要在持有全局锁时等待 socket 可写。

**验收：** 测试中让一个客户端停止读取，同时另一个客户端持续收发；应用待发送字节预算和 RSS 有可解释的上界，正常客户端延迟不随慢客户端无限增长；关闭慢连接后内存回落。WebSocket 排空时主动发送 [1001 Going Away](https://www.rfc-editor.org/info/rfc6455/) 并限时等待 Close 握手；不能保证跨副本无损迁移。

**面试讲法：** 区分“epoll 不阻塞线程”和“队列不会无限膨胀”；后者必须靠背压策略。

## 5. Redis Streams 跨副本事件通道

**最小演示：** 为一个房间建立有界保留的事件 Stream；每个副本以 `XREAD` 跟进该 Stream，把事件广播到**本副本**的 WebSocket 客户端。事件包含 Stream ID，客户端重连时提交最后已处理 ID 以补读并去重。不要把同一个 consumer group 用作广播：同组消费者会分担消息，而不是每个副本各得一份。[Redis Streams 文档](https://redis.io/docs/latest/develop/data-types/streams/)说明了 `XREAD`、消费者组、ID 和裁剪语义。

**验收：** 两个独立 HTTP/WebSocket 进程、一个 Redis 实例；A 发出的事件能到 B 的客户端；杀掉一个副本后另一个继续服务；重启并在保留窗口内补读。明确 Redis 不可用时的策略（拒绝发布或仅本地投递），消息可能重复，客户端按 ID 去重；裁剪后的缺口须返回可识别错误。不要宣称 exactly-once 或跨房间全局顺序。

**面试讲法：** 分清服务发现、连接路由和消息分发三个层次，解释为什么 Kubernetes Service 本身不能跨 Pod 广播 WebSocket 消息。

## 6. 故障注入与恢复矩阵

**测试底座：** 用可控的 Stream 适配器和本机代理注入分段读、延迟写、半关闭、RST、后端超时；保留随机种子与事件序列。每项功能的关键竞态优先用小型确定性测试，再补进程级测试。记录 `/proc/<pid>/fd`、活动 Fiber/连接计数、排空耗时和 p99，不只检查退出码。

**验收：** 形成“故障 → 预期响应 → 资源回收 → 恢复时间”的矩阵；CI 跑不依赖外部服务的故障用例，Redis 场景按可选依赖运行。失败时输出种子、负载参数和服务端日志，使问题可重现。

**面试讲法：** 用一次真实修复说明故障注入如何发现正常测试覆盖不到的取消或 fd 复用问题；没有发现前不要编造事故。

## 建议的交付节奏

- **第一阶段：** 先完成 1 的测量面板和 6 的最小故障底座。若 4 worker 退化根因明确，单独提交修复及对照数据。
- **第二阶段：** 完成 2、3、4，形成“超时 → 取消 → 限流 → 背压”的单机容量闭环。
- **第三阶段：** 完成 5，并在两进程 + Redis 的集成测试中演示故障与补读。真实 Kubernetes 集群运行是单独验收项；现有机器尚无 Docker/kubectl。
- **简历只写已验收结果：** 每项至少有公开接口、异常路径、端到端测试和可复现命令。性能数字必须注明负载、机器、构建类型及比较基线。
