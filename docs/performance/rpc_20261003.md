# RPC 性能复测：并发 16 / 32

日期：2026-10-03。代码版本 150c13f，Release。

## 环境与方法

- WSL2 Ubuntu 22.04，GCC 13.1.0，gRPC 1.30.2，libprotoc 3.12.4，可见逻辑 CPU 16 个。
- 内核：Linux-6.18.33.2-microsoft-standard-WSL2-x86_64-with-glibc2.35。
- 并发 16：每模式 20000 次计时请求、5 轮；并发 32：每模式 20000 次、3 轮。
- 合计 40 组、800000 次计时请求；每并发通道另预热 10 次。所有组错误为 0。
- 五模式逐组串行，每组新进程，偶数轮反转顺序；没有并行构建或故障测试。
- 业务延迟为 0；追踪记录、应用重试关闭，I/O 诊断开启，复用连接/channel。
- 同机回环、闭环负载，未固定 CPU 亲和性；两档按 16 后 32 的顺序运行。

结果为各轮指标的中位数，P99 是各轮 P99 的中位数，不是合并所有请求后重新计算的分位数。CPU 为累计进程 CPU 秒，可大于墙钟秒；服务端采样窗口包括客户端启动与预热。fd 为采样峰值。详细方法见 [基准说明](../rpc_benchmark.md)。

## 结论

1. 默认 worker 通知两档均零错误。直接 Fiber 客户端 fd 峰值在并发 16 为 31→15，并发 32 为 47→15。
2. 直接 eventfd 模式每轮 epoll_ctl 为 40320（并发 16）和 40640（并发 32），包含预热的添加与删除；worker 模式没有每 RPC 的 epoll 注册。HTTP 压测端计数不能代替网关内部诊断。
3. 增加并发没有使吞吐量翻倍，P99 上升。不同档位顺序与系统负载没有严格控制，不能据此推断精确的扩展效率或极限容量。
4. worker 通知的稳定收益是减少 fd/注册开销。吞吐量差异应结合各轮范围看待；未做统计显著性检验，不能承诺所有场景更快。
5. 同机、短时、闭环、无业务延迟测量不能代表跨机生产吞吐量，不能替代过载或长时间稳定性测试。没有独立 profiling 证据，不能仅凭表格断言某一函数是瓶颈。
