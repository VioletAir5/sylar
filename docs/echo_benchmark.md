# TCP echo 初始基准

## 运行

先编译 Release 版本，并在一个终端启动 `./build-release/sylar/echo_server 9000`。再运行：

```bash
python3 bench/echo_benchmark.py --port 9000 --clients 100 --requests 100 --bytes 64
python3 bench/echo_benchmark.py --port 9000 --clients 500 --requests 20 --bytes 64
```

脚本先建立所有连接，再让每个连接串行发送请求并验证回显，所有连接并发运行。耗时从连接完成后开始计，不含连接建立。延迟包含 Python asyncio 客户端、内核回环与服务端；每组总计 10000 次请求。

## 2026-09-28 初始结果

环境：同一台 WSL Ubuntu 主机上的回环 TCP；GCC 13.1.0，CMake Release，64 字节消息。单次运行，未控制 CPU 频率或后台负载。

| 并发连接 | 每连接请求 | 完成请求 | 吞吐（请求/秒） | p50 | p99 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 100 | 100 | 10000 | 12725 | 7.819 ms | 10.426 ms |
| 500 | 20 | 10000 | 12640 | 39.102 ms | 49.099 ms |

这两组数字只证明当前实现能处理这些并发连接并提供后续版本的同机对照。Python 客户端可能成为瓶颈；尚未测量服务端 CPU、内存和最大吞吐，也未对比其他框架。发布性能结论前，需要独立压测机、预热、重复运行和资源指标。

## 四工作线程的初步验证

使用同一 Release 构建、回环地址和 Python 客户端，启动命令为 `./build-release/sylar/echo_server 9000 4`。

| 并发连接 | 每连接请求 | 完成请求 | 吞吐（请求/秒） | p50 | p99 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 500 | 20 | 10000 | 12498 | 38.339 ms | 48.940 ms |
| 1000 | 10 | 10000 | 10717 | 82.400 ms | 136.014 ms |

1000 个连接全部成功回显。四工作线程在这个客户端与同机回环组合下没有表现出吞吐提升；不能据此判断服务端扩展能力，后续需独立压测机及服务端 CPU、内存测量。

## C++ 客户端并行对比（2026-09-28）

构建并复现：

```bash
cmake -S . -B build-release -DCMAKE_BUILD_TYPE=Release -DSYLAR_BUILD_BENCHMARKS=ON
cmake --build build-release -j
python3 bench/compare_echo.py \
  --server ./build-release/sylar/echo_server \
  --client ./build-release/bench/sylar_echo_bench
```

若 yaml-cpp 安装在自定义目录，CMake 还需传入相应的 `CMAKE_PREFIX_PATH`。负载为 4 个独立 C++ epoll 客户端进程，每个进程 250 个连接、每连接 100 次 64 字节回显；每轮总计 10 万次请求。服务端先预热，随后各跑 3 轮。计时从启动压测进程到所有进程完成，包含客户端进程启动和连接建立。主机为 WSL Ubuntu，可用 16 个逻辑 CPU；服务端和客户端仍在同一台机器上。

| 服务端工作线程 | 第 1 轮 req/s | 第 2 轮 req/s | 第 3 轮 req/s | 中位 req/s | 第 3 轮服务端 CPU 时间 | 第 3 轮 VmHWM |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 0（监听线程处理） | 43651 | 41620 | 39261 | 41620 | 2.400 s | 30808 KiB |
| 4 | 298639 | 280324 | 272665 | 280324 | 1.320 s | 21024 KiB |

在这个测试条件下，4 工作线程的中位吞吐约为单线程的 6.7 倍。单个 C++ 客户端进程压测 1000 连接时，4 工作线程反而更慢；该客户端只有一个事件循环，无法同时驱动所有工作线程。因此两种结果都保留，不能把 6.7 倍当作跨机器或其他消息大小下的通用加速比。

额外用 4 工作线程连续运行 10 轮、共 100 万次请求，全部成功。VmHWM 从约 16 MiB 上升到约 21.7 MiB 后，在最后 4 轮没有继续增长。这只是一项短时资源检查，不代替长时间稳定性测试。C++ 客户端的单进程输出包含 p50/p99 延迟；多进程汇总脚本只汇总吞吐、服务端 CPU 时间和 RSS 峰值，未合并全体请求的延迟分布。
