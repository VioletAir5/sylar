# 面试讲述：一次有证据、有撤回的性能调优

先阅读[完整实验报告](../performance/rpc_tuning.md)，亲手复现并定位代码。以下表述应据实结合自己的参与；实现使用了 AI 辅助，不能把未亲手理解的部分说成独立完成。

## 一分钟回答

我做过一次围绕可观测性开销的 RPC 调优。最初看到后端线程创建频繁，诊断负载下 1000 次请求创建 485 个线程。我试过增加同步 gRPC 的线程保留量，线程创建降到 12，但完整负载没有稳定变快，有些 P99 更差，所以没有改默认参数。

之后定位到追踪导出：原实现持共享锁编码整个 span ring，会阻塞业务记录。我先用不可变共享快照把编码移到锁外，记录操作 P99 从约 3.34 ms 降到 38 µs。但完整 RPC 尾延迟仍不好，因为 JSON 计算还占用 I/O worker。最后把导出放进独立线程，并用两个在途任务和 500 ms 等待预算约束它。

在持续抓取追踪数据的同机测试里，五轮中位数吞吐量从 7326 到 7785 请求/秒，P99 从 6.99 到 4.45 ms，全部零错误。代价是一个线程、约 1 MiB 额外 RSS 和快照引用成本。这是特定观测压力下的收益，不是所有负载或生产极限保证。

## 面试官可能追问

### 为什么先优化线程却没有采用？

线程创建次数只是代理指标。扩大空闲保留量也会改变锁竞争、调度与资源占用；真实吞吐量、P99 不一定改善。我做参数探索和交替对照后撤回默认修改，保留 opt-in 参数复现实验。不能凭单个计数选方案。

### 为什么锁外编码后，还要独立线程？

锁外编码解决其他线程 record 被阻塞的问题，却没有让当前 I/O worker 在 CPU 编码期间调度其他 Fiber。两者解决不同的竞争：共享锁和调度线程。完整链路测量暴露了第二层，不能只看局部基准。

### 锁释放后，ring 中的记录可能被淘汰，如何避免悬空？

记录为不可变共享对象，快照复制拥有引用。ring 可以移除自己的引用，但已开始的导出保留对象到编码结束。dropped 与快照在同一临界区读取；并发测试验证 JSON 内部字段一致。代价是记录延迟释放和额外控制块。

### 为什么不直接投递到无限任务队列？

BlockingExecutor 本身有队列，必须在调用前建立独立导出准入。最多两个任务，涵盖执行与排队。满额立即 503；如果等待者超时，任务可能仍在执行，permit 要留到实际完成，而不是局部返回时释放。

### 超时和停机如何避免资源生命周期错误？

导出 lambda 拥有 recorder 和 lease；lease 的成员销毁顺序保证 permit 先于 owner 销毁。调用者等待最多 500 ms，且继承父取消与 deadline。停机先停止路由使用者，再结束独立执行器，避免继续入队和原始指针被晚到调用访问。

### 微基准能证明整体变快吗？

不能。traceparent 编码从两次分配到一次、35.32 ns 到 19.97 ns，只证明该真实函数的局部成本下降。网络、gRPC、业务、排队仍占据其他时间。完整 RPC 测量另做，而且只有重导出场景展示了明确方向。

### 数字如何得到？有什么边界？

旧/新独立二进制交替，五轮；并发16、每轮3万业务请求，另有持久连接抓 /traces，容量4096，每次读取后等待20ms。不是精确50Hz开环输入。原始文件保留 SHA256、每轮延迟、CPU/RSS/fd 和导出数量。WSL同机、短时闭环、背景负载未完全隔离，不能声称统计显著或生产上限。

### 下一步怎样验证生产价值？

先在独立压测机、接近实际抓取频率和业务延迟下复现，再测长期稳定性和开放输入。当前没有这些结果，不能写成已完成。原始 gRPC 线程参数结论也依赖库版本，升级后应重测。
